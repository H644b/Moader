# v0.2.6-rc.1 hold-R candidate

This local candidate addresses reports that a successful Seedsow FS installation is followed by two native-game launches with **R** but no hbmenu. The installation receipt proves HEN reached its waiting state; it does not prove the later game-entry path.

The matched HEN now reads fresh R samples from the enabled standard controller styles as well as SystemExt. During first-launch policy capture, it waits for a still-closing Seedsow application to leave PM before binding the native game. The full regular kaiHEN file set, game loader, hbmenu, OunceShell and Moader app/resident remain in the backend kit. RO and bootstrap bytes are unchanged.

The pinned native build, patch replay, HEN host regressions and installer/setup checks pass. After bounded pre-FS misses, one fresh Demo boot installed the exact candidate. The owner reached hbmenu with two R launches and reported Moader runtime and FS connected. That console already had a saved game policy, so the path relevant to new users remains unverified and the build proof keeps `console_retest_passed: false`. A tester without an existing `/kaihen/bin/game/main.npdm` should use one fresh full reboot, install once, close Seedsow, then hold **R** through the first and second launches of the same native Switch 2 game. If hbmenu does not appear, preserve the GUI log and run directory privately. Do not rerun FS or HEN on a failed or uncertain boot.

After this candidate was packaged, an affected tester reported the same failure. Their archive confirms exact candidate installation and readback but has no post-game trace. The first-launch policy and takeover behavior therefore remain unresolved; this candidate must not be presented as a general hold-R fix.
