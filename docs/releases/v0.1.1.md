# Moader v0.1.1 — cumulative release

**Known unresolved system crash.** In the latest fresh-boot test, the matched backend installed, HEN/resident startup completed and the browser worked. Launching Minecraft Nintendo Switch 2 Edition without R unexpectedly opened hbmenu. The user closed that host with **HOME → X**, then another Minecraft launch produced **`2011-0102`**. **No Reload operation was requested that boot.** The cause remains under investigation; this does not rule out shared HEN, reload, filesystem or host-lifetime code.

v0.1.1 is a **regular release** with this known issue. The new app/resident are rebuilt with **0.1.1** labels and have **host validation only**. Successful installation or a running web page is not a verified fix for host exit, normal game launching or the complete reload lifecycle. [Detailed validation and limits](../VALIDATION.md).

v0.1.1 brings together **all changes since the first v0.1.0-dev release**, rather than only the changes after dev.4. It includes dev.1–dev.4 and the unpublished dev.5 development candidate. There was no published dev.5 tag. [Full comparison](https://github.com/H644b/Moader/compare/v0.1.0-dev...v0.1.1) · [cartridge/reload/installer changes in PR #7](https://github.com/H644b/Moader/pull/7).

## Changes since v0.1.0-dev

### Linux/WSL and macOS setup

Direct setup accepts a **fresh, verified held FS session from kurumuz's pinned ns2jb fork**, using a run directory and native Node 24. It supports Linux/WSL2 and macOS alongside the existing **mac2jb route on macOS**, which retains the exact bundled Node from its generated status command. Preparation creates a unique immutable snapshot and prints the matching install command; it does not acquire FS itself.

The guides explain WSL LAN/bind requirements, both directions of connectivity, Linux Node rather than Windows `node.exe`, and keeping acquisition/preparation in the same distro. They also separate the two helper routes so a mac2jb status command is not mixed with a direct-run preparation. Linux CI checks real precompiled-kit preparation against pinned inputs, with privileged/native operations blocked. These checks do not establish live Linux/WSL console installation or correct networking on every host. [Installation](../INSTALLATION.md).

### Experimental Civilization VII / CivSwitch entrypoint

The new `civ7-s8n` profile admits one exact pinned s8n source/materialized-run family and a current, verified **FS-only** held session. It adds authenticated bounded transport, source/run qualification, checked RO launch and diagnostic-process handoff, and Civ7's tagged-thread try-wait adaptation. Profile choice is bound to the prepared snapshot; source/proof mismatches and uncertain sessions cannot be overridden by relabelling them.

This is **host-qualified experimental integration**. No Moader acquisition, installation, resident/browser lifecycle or mod behavior through CivSwitch has been verified on a console. HerXayah and mac2jb CivSwitch runs are not admitted by this profile; that does not change mac2jb's separate SmileBASIC setup route. Read [CivSwitch requirements and limits](../CIV7.md) before choosing this entrypoint.

### Valid compressed ZIPs import correctly

The reader now handles the DEFLATE boundary case where the current 32 KiB input chunk is consumed just as the output buffer fills. Previously a no-progress empty-input pump could reject a valid archive before refilling the next chunk. Errors now identify the affected entry and zlib result.

Stream completion, CRC, declared lengths, size limits, safe paths and trailing-data checks remain required. Host regressions cover repeated/exact boundaries and malformed/truncated archives. Browser uploads run the **resident's** ZIP reader, so updating only the NRO leaves an older resident's decoder in use. This fix was introduced in dev.3 and does not diagnose the system crash.

### Library reads stay responsive; failed scans retain the last list

The app and browser read the last complete cached inventory during ZIP extraction instead of waiting for the import lock or repeatedly scanning every disabled payload. Conflicting library writes report **Busy** promptly. Availability withdrawal can continue while an import is extracting.

Failed enumeration/stat or a partial SD scan preserves the previous complete inventory with a separate warning and pauses unsafe mutations. It does not publish an unreadable directory as an empty library. Browser **Refresh** requests a full rescan; the resident retries in its background loop. A successful complete scan clears the warning. Concurrent native list changes retain the prior view until refresh succeeds.

Interface-operation errors, inventory warnings and the actual filesystem runtime result now have separate reporting. A stale selection or failed import no longer overwrites the FS runtime result and makes a healthy backend appear to have crashed. These improvements arrived in dev.4.

### Game-copy choices and the Z-A cartridge correction

Per-game **Settings → Game copy** is saved on the Switch and shared by the app/browser. Unspecified and Cartridge/game-key choices require repeated consistent observations of the matching inserted card. An explicitly selected digital copy checks installed noncard base Program content. Digital is the user's declaration of a card-independent copy, **not automatic ownership or license verification**; game-key downloads still require the matching physical card.

Unavailable or uncertain games are omitted from newly published replacement routing before their payloads are opened/validated. Requested toggles and library data remain saved. Details distinguish a blocked request, pending withdrawal, acknowledged omission and failed publication. The guard does not undo already loaded code/assets or instantly revoke old pinned filesystem objects.

Dev.4 incorrectly added an installed-content base-Program requirement after its matching-card check, falsely blocking Z-A. The physical-copy path now relies on repeated matching-card/owner observations without requiring that installed-content row. The digital path retains its noncard base Program checks. The corrected positive Z-A card case reached **Routing ready** on device; missing-card removal/withdrawal and general game compatibility were not accepted as tested. [Card checks](../CARTRIDGES.md).

### Protocol 7 cooperative resident reload

**Settings → Advanced → Reload Moader service** uses the matched protocol-7 HEN to restart one registered cooperative plugin. HEN stages and checks the replacement, serializes access to shared Loader resources, coordinates shutdown, waits for the exact old PID to disappear, launches one replacement and verifies startup/health before publishing its new PID/generation. Moader's health includes inventory readiness and a matching new runtime generation/FS acknowledgement.

Imports and active library writes can deny shutdown. The old process exits after its shutdown acknowledgement is sent. The app shows progress, reconnects to the replacement and treats lost replies as an existing operation to query. A quarantined or uncertain outcome does not authorize another replacement or a competing foreground writer. The browser connection closes while its resident process restarts; web auto-start preferences determine whether the replacement listener starts automatically.

Reload leaves FS-owned routing in FS. It does not reload the game, clear caches, make incompatible legacy plugins cooperative, or repair a system/FS failure. Two reload transactions completed on an earlier repaired candidate, followed by a failed normal-game launch. A later boot reproduced the fatal after HOME/X **without invoking Reload**. Neither observation establishes safe overall lifecycle behavior or excludes shared code as the cause. [Implementation and recovery limits](../PLUGIN_RELOAD.md).

### Native ownership and checked host restoration

The native changes retain SM proxy ownership across failed thread waits/closes and track GameArm's installed donor by entry, object and metadata rather than a reusable entry address alone. Expanded host fixtures execute production lifecycle/gate code with controlled transports and clocks. They remain simulations of kernel/FS behavior, not complete native resource accounting.

The host installer now uses an independent reader to observe the real Loader receive overwriting an armed receipt cookie before clearing the wake event. Signal/clear success or unrelated epoch movement alone is insufficient. Observations are bounded; uncertainty stops native cleanup/replay, and the proof retains restoration progress. The corrected installer passed a fresh console install, bootstrap and browser baseline. That is installation/startup evidence, not proof that the next game or host exit is healthy.

HEN and the flat bootstrap now ship as a source/patch-qualified **matched pair**. Setup, immutable snapshots and packaging validate both component identities against the build proof. The disclosure covers the complete kaiHEN patch, protocol additions, ownership changes and host adaptations. The native FS executable hook is unchanged by the reload feature. [kaiHEN changes](../KAIHEN_CHANGES.md).

### Guides and verification

The official Wiki is generated from the same installation, usage, troubleshooting, card, CivSwitch and contributor guides. Download links follow their release tag; issue templates identify the entrypoint. Build/package checks now qualify the native source/patch/HEN/bootstrap relationship, and the host suites cover route selection, immutable inputs, authenticated transports, malformed replies, ZIP boundaries, inventory recovery, availability, reload state and checked Loader restoration.

These checks preserve separate meanings for **implemented**, **host-tested**, **installed**, **started**, **acknowledged by FS** and **observed in a game**. Refer to [Validation](../VALIDATION.md) for exact evidence boundaries rather than interpreting a passing host suite as console acceptance.

## Updating matching components

- Keep `Moader.nro` and the resident `moader.nso` from this release together. Browser imports and library work execute in the running resident, so a new NRO alone cannot update those behaviors.
- Use the matching backend kit for the protocol-7 HEN/bootstrap pair and per-boot setup. An old running HEN cannot gain new commands merely because replacement files were copied to SD. Do not mix a stock bootstrap, another HEN build or a prepared snapshot from another host profile.
- Copying app/plugin files stages them; copying them does not activate FS hooks or replace running processes. The reload implementation is included for testing but is not a verified lifecycle-repair/update path. Follow the release's setup and recovery instructions with its unresolved crash in mind.
- Library requests, game-copy choices and preferences persist on SD. Privileged backend state is scoped to the current console boot. Uncertain native outcomes require the documented recovery boundary, not repeated use of an old session.

## What this release does not establish

The original bounded MK8 course-preview replacement/restore demonstration and normal close/reopen results belong to the original app/resident binaries. They have not been repeated on the rebuilt 0.1.1 pair. The matching HEN/bootstrap candidate has installation/startup evidence, while the complete host-exit/next-game lifecycle **failed**. The v0.1.1 app/resident version rebuild has no new hardware-validation claim.

There is no universal hot swap, automatic game-cache invalidation, arbitrary mod/firmware compatibility or reboot persistence claim. Same-size loose RomFS changes may affect later reads; cached assets, new/resized files, full images and executable mods have different reopen/relaunch requirements. A requested toggle, successful catalogue publication or zero payload rows does not prove what happened in a running game. The failure report's stale app/NRO cleanup files are not current teardown evidence.

The repeated `2011-0102` remains unresolved. Installation, two individually completed reloads, reproduction with zero reload requests, and valid diagnostic snapshots are useful evidence with different scopes; none alone proves a repair or rules out the changes consolidated here.
