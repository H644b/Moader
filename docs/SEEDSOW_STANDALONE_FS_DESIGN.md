# Standalone Seedsow: Moader FS installer candidate

This is the development boundary for the experimental [on-console route](SEEDSOW_STANDALONE.md). The first Profile B device run proved upstream FS promotion, HEN startup, hbmenu and Moader app launch. It did not install Moader's FS runtime: the current catalogue and the old acknowledgement had generation 136 but different epochs. The app therefore showed the filesystem backend disconnected. The PC-driven route installs that runtime separately in `tools/install-runtime.cjs` before its HEN handoff.

## Offline payload now available

`tools/seedsow-standalone-fs-payload.cjs` accepts an explicitly selected, previously verified native FS capture. It requires the exact sparse capture SHA-256 `0f58beb0a35ca2dadaf6300a8bbf4432974edfeac405aba4b3a3aa01af7d9271` and the 36 source-qualified Moader FS ABI ranges. It builds the zero-game dynamic Moader runtime from the existing native templates, a report template, 19 hook preimages/replacements and relocation tables. The output is local candidate data and is excluded from the source tree and published releases until device verification.

Two independent prior PC-driven captures produced identical payloads: 86,016 context bytes, 106,496 runtime bytes, 816 gateway bytes, 8,752 ABI bytes, four runtime, 19 gateway and 44 context address relocations. The generator applies its relocation tables at separate FS/context/runtime and source-object addresses, then compares them with independent `buildAll` and `buildContext` results. It also independently reassembles all 18 native call templates. This verifies the relocation format, not any console write.

## Candidate on-console adapter

The owner requires later boots to remain computer-free after initial SD/save preparation. `standalone/s2_moader.lua` now runs in the upstream Lua stage after replacement RO starts, while the retained FS endpoint and notifier are still owned, and before kaiHEN bootstrap. `tools/seedsow-standalone-overlay.py` changes only the three necessary save modules for the A path from a hash-pinned upstream checkout. It also gives B isolated original copies of upstream main/kaiHEN/RO, so B never invokes the Moader FS adapter; both buttons still share the matched SD kaiHEN files. `tools/seedsow-standalone.py` verifies the candidate payload hashes and stages its eight files beside the complete matched kaiHEN build. It uploads the two-slot save from a temporary copy of the pinned upstream uploader. The adapter attempts to:

1. Bind the owned promoted endpoint, FS process handle and replacement RO reader to the same current boot. Verify FS program ID, current code mappings, all required function bytes, untouched gateway/cave preimages and report ABI before any patch.
2. Open an owned SD filesystem and `/moader/runtime/runtime.log`; record object identity, method tables and reference baselines. Initialize the report, acknowledgement and log slots without borrowing an old epoch.
3. Allocate the context and executable backing in FS using the qualified native call bridge. Apply the offline payload's FS, context and runtime relocations using **observed** addresses, verify every transferred page, map RX code and publish it. No unchecked fixed ASLR address is admissible.
4. Retain the SD/report references exactly once, close temporary owners, stage gateways in the proved empty code cave, compare each of the 19 original instruction blocks, attach hooks, activate the runtime and verify idle counters and report writes. Preserve an uncertain owner and require a full reboot after any ambiguous native operation.
5. Signal FS hook readiness before kaiHEN bootstrap. Once Moader publishes a new catalogue, verify a CRC-valid FS acknowledgement with the **same current epoch and generation** before reporting a complete Moader installation. HEN READY alone is insufficient.

The PC-driven `runtime/modloader/lib/resident.cjs`, `native.cjs`, `context.cjs` and `source.cjs` are the behavior and ownership references. Host simulation found and fixed a 16 KB copy versus 4 KB mapping error; the corrected flow simulates all 26 executable page maps, five native calls, 19 hook replacements, metadata reset and final notifier restoration from the exact capture. The preflight also rejects changed FS code and occupied caves before a write, and retains the owner after uncertain RO transport. These are host results.

The next fresh-boot A run passed those method-table reads. Its SD log records allocation of the resident context, mapping of all 26 RX pages and exact retention of the SD and report references, then `MOADER FS: resident runtime is busy or its report write failed`. The screen again stayed at ABI read 6/36 because the frame buffered later lines. Read-only SD inspection found a 417-byte runtime report ending with `Loader active`, while the 64-byte catalogue and acknowledgement remained zero. The adapter's combined check did not log its three values, so the specific failing field was unobserved. Source inspection shows that `lfs_read` increments `active` before copying requested FS memory and decrements it after the reply; the retained IStorage used by `read_fs` therefore sees its own in-flight read as one. The PC-driven installer uses a separate process-memory helper for its zero-active check. The on-console adapter then required two successive snapshots each with `active=1`, no reader errors and a one-call increment, plus a zero report-error flag. The host flow modeled this self-counted read and passed. That used boot was powered off; HEN completion and same-boot Moader connection remained pending.

The next fresh-boot A run again showed ABI read 6/36 on screen, but its SD log reached the new diagnostic: `calls=14/16 active=1/1 errors=0/0 report=0`. The only failing condition was the assumed one-call increment. The upstream `read_fs` implementation first calls `ep_storage_read` to validate its descriptor, then calls it again for the payload. Both are counted by the active `lfs_read` hook, so two consecutive payload snapshots advance `calls` by exactly two. The adapter and host flow now require that observed two-call delta while retaining the active/error/report gates. This corrected check passed host source guards and the exact-capture flow. The used boot was powered off before SD inspection; a new A run is required to establish the next device state.

The following fresh-boot A run passed all 36 code checks and empty-cave checks, then stopped before resident allocation at `FS program registry is unavailable`.
